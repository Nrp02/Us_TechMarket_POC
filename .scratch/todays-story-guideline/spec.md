# An editable analysis guideline for Today's Story

## Problem Statement

The `todays-story-reasoning` ticket removes the rules that were forcing Today's Story's sections into pure restatement, but removing a restriction isn't the same as teaching the model how to reason well with the room it's now given. Left only with "you may now reason freely, grounded in the input," the model has no consistent *method* — nothing telling it to look at context before attributing cause to the company, nothing telling it to be honest about what a given explanation does and doesn't account for, nothing steering it away from overclaiming causation just because two facts happened to land on the same day. Without that, quality will vary section to section and stock to stock. Separately, tuning *how the model is told to reason* shouldn't require editing the same function that assembles structured JSON input — those are two different kinds of change with different edit frequency and different risk, and mixing them into one function makes both harder to review.

## Solution

Add a small, separately-editable "analysis guideline" — a written set of reasoning principles, informed by how professional equity analysts actually approach daily stock commentary (researched, not invented from scratch), translated into rules that only ever reference data already present in Today's Story's structured input. It lives in its own module, imported into the prompt-building function and interpolated into the final prompt text, so editing the reasoning guidance never requires touching the JSON-schema-assembly code around it.

## User Stories

1. As a visitor, I want sections that discuss sector/peer/market context to establish that context before attributing a move to the company specifically, so the narrative follows a sound order of reasoning rather than jumping straight to a company-specific claim.
2. As a visitor, I want a stock diverging from its peers treated as a signal that needs corroboration (from volume, fundamentals, or news) before the narrative calls it "genuine company-specific strength," so an isolated, unconfirmed divergence isn't overstated as a settled read.
3. As a visitor, I want an explanation to say plainly what it does and doesn't account for when the data only partially supports a clean story, so the narrative doesn't force a tidier account than the evidence actually gives it.
4. As a visitor, I want descriptive language ("this move is unusual relative to its own history," "the stock diverges from its sector") used as the primary claim, with causal language reserved for when the data genuinely supports it, so the narrative reads as careful observation first and interpretation second.
5. As the project owner, I want the guideline sourced from how real equity analysts reason (researched, cited, not guessed), so its content isn't just my or the AI's improvised idea of what "sounds analytical."
6. As the project owner, I want every principle in the guideline scoped strictly to fields that already exist in Today's Story's structured input (price, volume, peers, sector/market divergence, volatility percentile, 52-week range, YTD/MTD, fundamentals growth/surprise, news), so research doesn't introduce a reasoning pattern that needs data the product doesn't have (P/E ratios, analyst consensus, technical indicators like RSI/MACD are explicitly out).
7. As the project owner, I want the guideline to live in its own file, imported by the prompt-building function, so changing the reasoning guidance is a one-file edit that never touches the function assembling the JSON schema and input data.
8. As the project owner, I want this guideline's content to compose with, not duplicate, the rules already decided in the `todays-story-reasoning` ticket (no invented facts, no new numbers, no predictions, no investment advice, no repeating a conclusion an earlier section already made) — the guideline adds *method*, the existing rules remain the hard boundaries.

## Implementation Decisions

- **New module**: a single exported constant holding the guideline text, in its own file (a plain TypeScript string export — the same convention this codebase already uses for its other prompt-adjacent constants, e.g. the fixed fallback lines already defined alongside the narrative-generation code). No runtime file-reading, no markdown file loaded at request time — editing the guideline is a one-file code edit, same review/deploy path as everything else in this codebase, chosen over a runtime-loaded file for zero added complexity in a serverless function.
- **Where it's used**: imported into the prompt-building function and interpolated into the assembled prompt text, alongside (not replacing) the per-section instructions and the hard rules already decided in `todays-story-reasoning` (grounding-only, no invented facts, no predictions/advice, anti-redundancy). The guideline is *general method*; the per-section instructions remain the place that says which JSON key means what.
- **Guideline content, derived from research** (see Further Notes for sourcing) and restated only in terms of fields already present in Today's Story's structured input:
  1. **Context before attribution**: when a section discusses peer, sector, or market data, establish what the group/peers did before making any claim about the company specifically — mirrors the researched pattern of studying the group before the company.
  2. **A lone divergence needs corroboration, not just observation**: if the stock's move diverges from its peers or sector, that divergence alone is a signal, not proof of genuine company-specific strength — the narrative should look for whether volume, fundamentals, or news corroborate it before treating it as a settled read, and say plainly when nothing else corroborates it.
  3. **State what an explanation covers and what it leaves open**: when connecting news, fundamentals, or peer/sector behavior to the day's price move, the narrative should be explicit about which part of the day's data the explanation accounts for and which part (if any) it doesn't — a partial, honest account is preferred over a complete-sounding one that quietly ignores a data point that doesn't fit.
  4. **Describe before you attribute cause**: default to descriptive, observational phrasing (what happened, how it compares, how unusual it is) as the primary claim in every section; causal language is a secondary layer used only where the existing grounding rule already permits it (still bound by every rule `todays-story-reasoning` already locks in — this principle is about *default phrasing style*, not a new exception to causal-claim scope).
  5. **A statistically unusual day is not evidence of a persisting trend**: volatility percentile, relative volume, or a large price move describe today, not tomorrow — this principle exists to reinforce (not duplicate) the already-locked "never predict future prices or trends" rule at the phrasing level, since a strongly-worded description of an unusual day can drift into implying persistence without ever using a literal prediction.
- **Composition with `todays-story-reasoning`**: this ticket supersedes that ticket's Implementation Decisions only on *where the reasoning-instruction text lives* (a guideline module, not inline in `buildPrompt`) — every other decision in that ticket (removing the causation wall project-wide, removing the sentence cap, the "What Happened" widening, the relative-volume figure, the `news_summaries` wiring, the fundamentals bug fix) is unchanged and this ticket does not re-decide any of it.

## Testing Decisions

- No automated test seam — the guideline is a plain exported string constant with no logic of its own, same as this codebase's existing prompt-adjacent constants (the fixed fallback lines), none of which have dedicated tests; correctness here means the *content* is right, which isn't something a unit test can assess.
- Verification is manual, folded into `todays-story-reasoning`'s existing verification step (spot-checking generated sections against raw data): specifically confirm that a section discussing peer/sector divergence establishes context before attributing cause, that a section with only partial supporting data says so explicitly rather than forcing a clean story, and that no section drifts into implying future persistence of an unusual move.
- Type-check and lint clean, as usual.

## Out of Scope

- Any guideline content referencing data not already in Today's Story's structured input (valuation multiples, analyst consensus/ratings, technical indicators) — explicitly excluded per the research-scoping decision made before research began.
- Per-section guideline variants tuned individually through separate research passes — this ticket produces one holistic guideline informing all sections consistently, not seven independently-sourced frameworks.
- Any change to the hard rules already locked in `todays-story-reasoning` (grounding, no invented facts, no new numbers, no predictions, no investment advice) — this ticket adds reasoning method on top of those rules, it doesn't renegotiate them.
- A runtime-editable (non-code-deploy) guideline mechanism — deliberately rejected in favor of a plain code constant; revisit only if editing frequency in practice turns out to need it.

## Further Notes

- Research was scoped to one holistic web search (not per-section, not a deep literature review — a deliberate, agreed-in-advance scope for a school-project timeline) covering how equity analysts approach daily stock commentary: relative strength/peer comparison, distinguishing genuine company-specific moves from unconfirmed signals, and reconciling an explanation against the full set of evidence. Sources: MarketSmith's "When everything is weak, ask what the comparison really says," "The first question is not which stock is strongest," and "The chart that survives alone may be asking for more work" (marketsmithin.substack.com); StockCharts.com's ChartSchool entry on Price Relative/Relative Strength.
- This is one of three follow-up tickets from the same extended grilling session that produced `todays-story-reasoning`; the other two (`sec-filings-signal`, `todays-story-cards`) are independent of this one and can land in any order.
- The file-format decision (a plain TypeScript constant, not a runtime-loaded markdown/text file) was made directly in this spec rather than put back to the owner as an open question, after an earlier round on this same topic was interrupted before it was answered — flagged here explicitly so it's easy to challenge if it's wrong, rather than buried as an assumption.
